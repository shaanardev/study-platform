# Overview
  - Lakeflow Jobs allows you to orchestrate every type of workload within Databricks, including notebooks, SQL queries, dashboards, pipelines, and much more.
  - [orchestration](./orchestration.png)
    - The left panel shows multiple options including open source solutions (Apache Airflow, Prefect, Dagster, dbt), cloud-native services (AWS, Azure, Google Cloud), and custom in-house frameworks.
    - Diagram on right illustrates a typical data workflow with multiple steps: ingesting sessions and clicks data, joining them, performing featurization and aggregation, analysis, and training models. Then you have various downstream uses including BI and Data Warehousing, Data Streaming, and Data Science and ML.
    - The question mark in the diagram represents a critical challenge: there are many ways to orchestrate these workloads, but which approach is best?
  - It's difficult to work with external orchestration tools because they introduce productivity, quality, and reliability challenges.
  - key benefits of lakeflow jobs
    - simple authoring
    - actionable insights
    - proven reliability. Because it's native to the platform, it integrates seamlessly with data ingestion and transformation, the processing engine (Photon), governance (Unity Catalog), storage (Delta Lake), data warehousing, and machine learning capabilities.
  - [architecture](./lakeflow-job-architecture.png)
    - workflow engine at the cetner coordinates everything
    - compute layer supports various workloads; ETL, ML/AI, Analytics/BI operations
    - multiple trigger types: Scheduled (time-based), Continuous (always-running), File Arrival (event-driven), and Table Updates.
    - Observability for monitoring and troubleshooting, 
    - Control Flow for managing task dependencies and execution order.

# Core Components
- [jobs](./jobs-component.png)
  - primary resource for scheduling, coordinating, and running operations such as data processing, ETL, analytics, and machine learning workloads within the Databricks environment.
  - job result determined based on its leaf tasks
  - can be marked Succeeded with failures when some non-leaf tasks fail but all leaf tasks succeed
- [tasks](tasks-component.png)
  -  a single unit of work within a job that executes a specific workload such as a notebook, script, query, and more. Tasks are the individual building blocks that do the actual work.
- each job consists of one or more tasks, which are the individual units of work that make up the job.
- task configuration options; defining path, add libraries, add parameters, enabling notification
- task types
  - notebook; you get options like specifying the Source path to your notebook, choosing Compute options (cluster configuration), and many more settings specific to running notebooks.
  - sql task; specify the SQL task details, write or reference your SQL query, and select the SQL warehouse that will execute your query.
- jobs orchestration
 - [tasks](./job-orchestration-tasks.png)
 - [control flow](./job-orchestration-control-flow.png)
 - [triggers](./job-orchestration-triggers.png)
 - shows how tasks can be connected with different control flow patterns
 - implement Sequential execution (one after another), Parallel execution (multiple tasks at once), Conditional execution with If/else logic, Run Job tasks for modular design, and For each loops for iterative processing.
 - trigger types; manual triggers for on-demand execution, Scheduled triggers using cron expressions, API triggers for programmatic execution, File Arrival triggers for event-driven processing, Table triggers for data change events, and Continuous triggers for streaming workloads.
- [compute options](./compute-options.png)
  - Interactive Clusters can be shared by multiple users and are best for ad-hoc analysis, data exploration, or development. However, they should not be used in production as they are not cost-efficient
  - Job Clusters are approximately 50% cheaper as they terminate when the job ends, reducing resource usage and costs. They're ideal for production workloads, though they are subject to cloud provider start-up times. With Databricks Jobs, you can reuse the same cluster across tasks for better price performance.
  - Serverless provides a fully managed service that is operationally simpler and more reliable. It offers faster clusters and auto-scaling capabilities, providing better user experience for lower cost. With out-of-the-box performance optimizations, Serverless provides lower overall TCO
  - SQL Warehouse is purpose-built for SQL queries, dashboards, and BI, and is serverless by default. It offers high concurrency and autoscaling via Intelligent Workload Management, with auto-start/auto-stop and adjustable cluster sizing to help control costs.
- [selecting compute](./selecting-compute.png)
  - this diagram illustrates an important principle: A job can have one or more tasks inside it, and each task can be assigned its own compute resource. Tasks in the same job can either share the same compute or use different compute as required.
  - you might have Task-1 running on an All Purpose Cluster, Task-2 on Serverless, Task-3 on a Job Cluster, and so on. This flexibility allows you to optimize both performance and cost for each specific task.
- [task orchestration](./task-orchestration.png)
  - run multiple tasks as a Directed Acyclic Graph (DAG)
  - orchestrate tasks using the Databricks UI, API, SDK, or Declarative Automation Bundles.
  - diagram shows Task-4 depends on Task-1, Task-4 depends on Task-2 and Task-3, and Task-3 depends on Task-1. You define the order of execution by configuring these task dependencies, creating a DAG of task execution.
  - [common workload patterns](./task-orchestration-common-workload-patterns.png)
    - Sequence Pattern is used for data transformation, processing, cleaning, and building bronze/silver/gold tables in a medallion architecture.
    - Funnel Pattern brings together multiple data sources for data collection and consolidation.
    - Fan-out or Star Pattern takes a single data source and distributes it for data ingestion and distribution to multiple downstream systems.

# Creating & Scheduling Jobs
- configuration options
  - parameters & dynamic value references;  create reusable, adaptable tasks that can behave differently based on input values or runtime context.
  - notifications; giving you granular control over who gets notified about what events.
  - retries; protect against transient failures, different retry strategies depending on the criticality and expected failure patterns of different parts of your workflow.
  - task parameters; key-value pair defined at the task level.
    - specific to each task and allow for fine-grained control over task behavior.
    - support advanced orchestration such as; 
      - Conditional execution; which branches of your workflow execute based on data conditions, environment settings, or business rules.
      - looping; control iteration counts, define arrays for for-each loops, and manage complex processing scenarios.
      - passing context between tasks; Share information between tasks by setting parameters that downstream tasks can read, creating a data flow alongside your control flow.
  - Job parameters; key-value pair defined at the job level and pushed down to all tasks.
    - defined at the job level that provide default values for the entire workflow.
    - Applied to all tasks in the job automatically.
    - Provide common defaults across tasks.
    - Can be overridden at runtime when triggering job runs.
    - Can be used for different environments, date ranges, or processing modes.
    - automatic application; every task in the job automatically receives these parameters, eliminating the need to manually configure common settings across multiple tasks.
    - override capability; tasks can still define their own parameters with the same key names, but job parameters take precedence, giving you centralized control.
    - Runtime flexibility; you can override job parameters when triggering job runs, allowing the same job definition to behave differently for different scenarios — perhaps different environments, date ranges, or processing modes.
  - Job parameters automatically propagate to all tasks within that job. This creates an inheritance model where common defaults can be set while still allowing task-specific overrides.
  - Retrieving in Notebook Tasks: Use `dbutils.widgets.get("parameter_name")` to access both job and task parameters. The system automatically handles the precedence - if both job and task parameters exist with the same key, you'll get the job parameter value
  - Language-Specific Retrieval: Remember that parameter retrieval methods vary by task type. SQL tasks access parameters differently than Python wheel tasks or JAR tasks. Always check the documentation for your specific task type.
  - dynamically setting and accessing task parameters
    - setting; use `dbutils.jobs.taskValues.set(key="computed_result", value="some_calculated_value")` to store results that other tasks need. This might include record counts, processing status, file paths, or any computed information.
    - retrieving; use `dbutils.jobs.taskValues.get(taskKey="upstream-task-name", key="computed_result")` to access values from specific upstream tasks. This creates explicit dependencies between tasks based on data, not just execution order.
    - Unlike parameters which are set before execution, task values are created during execution, making them ideal for decisions that depend on processing results.
  - dynamic value references
    - referencing values at runtime from the job and task context 
    - These references use `{{ }}` notation and allow workflows to adapt to different execution. 
    - `{{job.start_time.day}}` - Access execution timing for date-based processing
    - `{{job.run_id}}` - Unique identifier for tracking and logging
    - `{{job.parameters.environment}}` - Access job-level parameters dynamically
    - `{{task.name}}` - Useful for logging and dynamic path generation
    - `{{task.retry_count}}` - Track retry attempts for debugging
    - `{{tasks.data-validation.values.record_count}}` - Access computed results from upstream tasks
    - `{{tasks.file-processor.values.output_path}}` - Use dynamic paths generated by other tasks
  - notifications
    - job level; apply to the overall job run. A success alert is sent when the job completes successfully, after all relevant tasks have finished.
    - task level; apply to individual tasks. A success alert is sent each time the configured task completes successfully.
    - [Design your notification strategy based on operational needs](./designing-effective-notification-strats.png), not technical convenience. Consider who needs to know what, when they need to know it, and what actions they can take based on the notification.
    - treats that state as successful for job-level success notifications, so task-level failure alerts may still be necessary if you need to detect every failed task
  - retry policies
    - policy determines not just how many times to retry, but under what conditions and with what timing patterns.
    - Consider factors like:
      - Failure Type: Transient network issues might warrant immediate retries, while data quality issues might not
      - Resource Impact: Retrying resource-intensive tasks too aggressively can cause cluster resource contention
      - Downstream Dependencies: Failed tasks might impact other workflows, making retry timing critical
      - Business SLA: Some processes have strict timing requirements that limit retry windows
  - schedules and triggers
    - rule that automatically starts a job run based on a specific condition or schedule.
    - fundamentally a rule engine that automatically initiates job execution based on specific conditions or schedules
    - principle; building reliable, responsive data systems that can operate autonomously.
    - trigger types include:
      - Time-based schedules: Traditional cron-style scheduling for predictable, recurring workloads
      - Continuous execution: Always-on processing for streaming data scenarios
      - File arrival events: Event-driven processing that responds immediately to new data
      - Manual triggers: On-demand execution for development, testing, and ad-hoc analysis
    - enable automation, so jobs can run without manual intervention, 
    - triggers eliminate human intervention points that can cause delays, errors, or missed executions. 
    - enable 24/7 operation and ensure consistent execution regardless of team availability.
    - Each trigger type has different reliability characteristics and failure modes. Understanding these helps you choose the right trigger for each use case.
    - scheduled triggers
      - Run jobs automatically at defined times or intervals.
      - Use the UI's common scheduling options for hourly, daily, weekly, or monthly runs.
      - Use cron expressions for more specific schedules, such as every 15 minutes during business hours or the first Monday of each month.
      - Set the appropriate timezone, especially when the business operates across regions.
      - Common uses:
        - Daily ETL to process the previous day's data.
        - Weekly report generation.
        - Monthly KPI aggregation.
        - Recurring maintenance tasks for streaming jobs.
    - file arrival triggers
      - Start a job when new files are detected in a configured storage location, rather than waiting for the next scheduled run.
      - Supported locations include AWS S3, Azure Storage, Google Cloud Storage, and Databricks Volumes.
      - Configure file patterns to select relevant files and avoid processing temporary or incomplete uploads.
      - Advanced settings can control the minimum time between triggers and how long to wait after the last change.
      - Useful for partner data feeds, irregular IoT uploads, trading data, and application logs.
    - continuous triggers
      - Keep a job processing by starting another run when the previous run finishes or fails.
      - Databricks manages built-in retry behavior for transient failures.
      - Intended for workloads that should remain active, especially streaming jobs.
      - Common uses include real-time analytics, fraud detection, IoT ingestion, and change data capture.
      - Monitor continuous jobs as long-running workloads; their operational needs differ from jobs that run and complete on a schedule.
    - manual triggers
      - Run a job on demand without a schedule or event trigger.
      - Start runs from the UI, API, CLI, SDK, or Declarative Automation Bundles.
      - The UI supports running with the job's current settings or overriding parameters for a run.
      - Useful for development, debugging, backfills, urgent processing, recovery, and production validation.
      - A manual trigger can be combined with other trigger types later.
    - table update triggers
      - Start a job when one or more specified tables are updated.
      - Can monitor for inserts, updates, deletes, or merges.
      - Configure the tables to watch and whether to trigger when all watched tables or any watched table is updated.
      - Advanced settings can limit the minimum time between triggers and set a wait after the last change.
      - Supports event-driven processing from table changes, reducing reliance on cron schedules and unnecessary runs when no new data is available.
  - conditional and iterative tasks
    - run-if conditional
      - control task execution based on the outcomes of upstream tasks, enabling workflows that can handle partial failures and complex dependency scenarios.
      - provide fine-grained control over task execution based on the outcomes of upstream tasks. 
      - you can define specific conditions that must be met for a task to run.
      - can prevent cascade failures and allows workflows to continue processing even when some components fail
      - helps mirror real-world business processes where multiple paths to success exist and partial failures do not halt the entire operation.
      - available Dependency Conditions;
        - all succeeded: This traditional dependency requires all upstream tasks to complete successfully before the next task can run.
        - at least one succeeded: This condition is useful when you have redundant data sources or processing paths, allowing the workflow to proceed if even one of the required upstream tasks is successful.
        - none failed: This allows a task to execute even if some upstream tasks were skipped, as long as no upstream tasks have explicitly failed.
        - custom combinations: This option enables the implementation of complex business logic that requires specific combinations of task outcomes.
    - If/Else Tasks 
      - boolean conditional logic directly in your workflow
      - allowing branches based on data conditions, processing results, or business rules.
      - boolean operators (==, !=, >, >=, <, <=) evaluate expressions against task results, parameter values, or computed metrics.
      - execution requirements; the condition "If none of dependency failed and at least one task executed" ensures that conditional evaluation only occurs when meaningful upstream results are available.
      - true/false branches; each branch can contain multiple tasks, enabling complex processing paths based on conditional outcomes.
      - business logic examples:
        - data Quality Gates: Branch based on record counts, null percentages, or validation results
        - processing Volume Decisions: Use different processing strategies for large vs. small datasets
        - environment-Specific Logic: Execute different tasks based on environment parameters
        - business Rule Implementation: Implement complex business rules directly in workflow logic
    - for each tasks
      -  iterative processing patterns where the same logic is applied to multiple data partitions or parameters, with configurable parallelism for performance optimization.
      - loops over an input array, passing each item as {{ input }} to the nested task. This creates clean, parameterized processing where the same logic handles different data partitions.
      - Configurable concurrency allows multiple iterations to run simultaneously, dramatically improving performance for independent processing tasks.
      - downstream tasks depend on the completion of the entire For Each container, not individual iterations. This simplifies dependency management while ensuring all iterations complete before downstream processing begins.
      - use cases
        - geographic processing; process data for each state/region in parallel
        - time period processing; handle different date ranges with the same logic
        - customer segment processing; apply the same analysis to different customer segments
        - file processing; process multiple files with identical logic
      - container concept
        - a single logical unit in your workflow, even though it executes multiple iterations internally. Understanding the container concept requires distinguishing between two components
        - for each container
          - top-level task manages the iteration logic, input array processing, concurrency settings, and resource allocation. It defines how many iterations run in parallel and how the input array is processed.
          - acts as a single logical unit in your workflow, even though it executes multiple iterations internally.
          - allows downstream tasks to depend on the For Each container rather than on each individual iteration, keeping workflow diagrams clean and manageable.
          - manages resource allocation across iterations, optimizing cluster utilization and preventing resource conflicts.
        - nested task/s
          - the actual work that gets performed for each iteration. It can be any task type—such as a notebook, SQL task, or Python script.
          - receives each array item as `{{input}}` and processes it according to your business logic.
        - This separation allows you to configure iteration behavior independently from the processing logic, making For Each tasks both powerful and maintainable.
  - handling failures
    - repair allows re-runs and overriding task params
    - reduces the time & resources required to recover from failed job runs
    - in case of task failure you can; modify & rerun or modify params and rerun
    - by rerunning only failed tasks, you minimize unnecessary computation and reduce costs, especially important for large, complex workflows.
    - running only failed tasks instead of entire workflows can reduce recovery time by 80-90% in complex pipelines, saving both time and money.
    - smaller recovery operations have less impact on system resources and reduce the risk of cascading failures during recovery attempts.
    - teams can respond to failures more quickly when they don't need to wait for entire workflows to complete, improving SLA adherence and business responsiveness.
    - **note** that fixing a task does not mean fixing a job.
    - recovery scenarios;
      - config fixes; correct param values that caused task failures
      - resource adjustments; increase memory or compute resources for tasks that failed due to resource constraints
      - code updates; deploy fixes and rerun only affected tasks
      - data quality issues; adjust processing logic to handle data quality problems discovered during execution
    - post repair run
      - audit trail; visibility into what was repaired, when, and by whom, providing essential information for troubleshooting and process improvement.
      - success validation; clear indication of which tasks were recovered successfully, enabling confidence in the repair process.
      - learning oppurtunities; historical repair data helps teams identify patterns in failures and improve initial job design to prevent future issues.
    - monitoring job performance
      - `system.lakeflow` system table
        - readonly catalog of all job activity across workspaces in the region 
        - all job activity across all workspaces in the region is automatically logged, providing complete visibility into workflow execution patterns and performance trends.
      - timeline tables slice long runs hourly using `period_start_time` and `period_end_time`, enabling reliable duration, concurrency, and SLA analytics.
      - `job_tasks`; task basic definitions
      - `job_run_timeline`; each job run over time
      - `job_task_run_timeline`; each task run over time
      - `Pipelines`; pipelines basic info
      - enables sophisticated analytics including cost analysis, performance trending, SLA compliance tracking, and resource utilization optimization.
      - spark ui
        - timeline analysis; The execution timeline highlights task duration, overlap, and bottlenecks, enabling quick identification of performance issues.
        - task-level details; Clicking individual tasks reveals; execution timestamps, resource utilization, cluster configuration, logs, I/O statistics
        - query performance details; Detailed query analysis shows; execution plans, optimization decisions, file access patterns, partition information, data spill details
        - actionable insights;
          - high planning time; May indicate a need for better partitioning strategies or metadata optimization.
          - high execution time; May suggest opportunities for join optimization, broadcast strategies, or skew handling.
          - resource bottlenecks; May identify memory, CPU, or I/O constraints that require cluster configuration adjustments.
  - prod best practises
    - compute strategy: Selecting the right compute options for performance, cost, and operational requirements.
    - implementing architecture patterns that support maintainability, reusability, and team collaboration.
    - version control and deployment practices that ensure consistency and enable CI/CD workflows.
    - proactive monitoring and optimization strategies that ensure SLA compliance and cost efficiency.
    - selecting compute
      - interactive clusters
        - best for performing ad-hoc analysis, data exploration or development but not prod
        - costly for job runs; interactive clusters remain running even when not executing jobs, leading to unnecessary costs
        - limited scalibility; shared resources can create contention and performance unpredictability
        - availability could be an issue due to parallel usage; multiple users sharing clusters can cause resource conflicts and job delays
      - job clusters
        - cheaper; terminates when job ends reducing resource usage & costs, eliminates idle resource costs
        - dedicated Resources: Each job gets dedicated compute resources, ensuring predictable performance
        - start up latency (cold starts); 
        - subject to cloud provider start up time; can delay job execution, requiring consideration in SLA planning
        - maintenance burden; more configuration and management compared to serverless options
      - serverless
        - simplicity; optimal choice for most production workloads because it provides operational simplicity, performance optimization, reliability and speed, and cloud independence.
        - you no longer need to choose the VM type. Customers do not need dedicated skilled DevOps folks.
        - high efficiency; [Photon](https://www.databricks.com/product/photon) turned on default.
        - faster startup; VMs run in Databricks account. We ensure enough nodes are available based on historical data and ML.
        - reliability; shielded from cloud disruptions
    - pricing structure
      - [traditional pricing model](./classic-pricing.png);  
        - multiple cost components:
        - direct costs; DBUs paid to Databricks plus infrastructure costs paid directly to cloud providers, including VMs, networking, and security services.
        - operational overhead; Often-overlooked but significant costs, including time spent on infrastructure deployment, automation development, maintenance activities, cost monitoring, and efficiency optimization.
        - hidden complexity; Managing multiple billing relationships, optimizing across different cost categories, and maintaining expertise in cloud infrastructure management.
      - [serverless pricing model](./serverless-pricing.png);
        - fundamentally simplifies the cost model:
        - unified billing; A single DBU price that includes infrastructure and operational costs, eliminating the need to manage multiple vendor relationships and cost optimization strategies.
        - value proposition; The fully managed service provides operational simplicity and reliability improvements that often justify higher per-unit costs through reduced operational overhead.
        - performance benefits; Auto-scaling capabilities and out-of-the-box optimizations often deliver better performance at a lower total cost than self-managed alternatives.
        - TCO advantages; When operational overhead is included, the total cost of ownership is typically lower with serverless, especially for organizations without dedicated platform engineering teams.
    - [modular design](./modular-design.png)
      - modular orchestration transforms large, monolithic workflows into maintainable, reusable components
      -  decomposition strategy
        - break complex DAGs into logical business units rather than technical components.
        - each module should represent a cohesive business function that can be developed, tested, and deployed independently.
      - parent-child relationships
        - Parent jobs orchestrate child jobs
        - creating a clean separation of concerns while maintaining overall workflow coordination.
      - benefits realization;
        - maintainability; Smaller jobs are easier to understand, modify, and troubleshoot.
        - reusability; Child jobs can be reused across multiple parent workflows.
        - team collaboration; Different teams can own different modules while collaborating on the overall workflow.
        - testing; Individual modules can be tested independently, improving quality and reducing deployment risk.
    - [git](./version-control-git.png)
      - change management; prevents unintentional changes to production jobs by ensuring all modifications go through proper version control processes.
      - single source of truth; eliminates confusion about which version of code is running in production by always executing committed code from specific branches or tags.
      - CI/CD integration; enables automated testing and deployment pipelines that can validate changes before they reach production environments.
      - platform support; broad compatibility with GitHub, GitLab, AWS CodeCommit, and other Git providers ensures integration with existing development workflows, regardless of the chosen platform.
      - collaboration benefits; multiple developers can collaborate on workflow development using standard Git workflows, including branches, pull requests, and code reviews, while maintaining production stability.
    - [compute & cost optimization practices](./three-pillar-best-practises.png);
      - production compute; Always use job clusters or serverless compute in production environments to ensure cost efficiency and resource isolation.
      - interactive cluster avoidance; Reserve interactive clusters strictly for development and ad hoc analysis to prevent production cost overruns and resource conflicts.
      - photon enablement; Enable Photon acceleration across all eligible workloads for significant performance improvements and cost reductions.
      - cluster reuse; Design workflows to reuse clusters across tasks when possible, reducing startup overhead and improving cost efficiency.
    - [orchestration & modularity practices](./three-pillar-best-practises.png);
      - modular architecture; Break complex pipelines into logical, maintainable modules using the Run Job task pattern for better maintainability and team collaboration.
      - multi-task design; Leverage multi-task jobs for parallel execution and improved resource utilization while maintaining workflow clarity.
      - advanced logic; Implement sophisticated business logic using Run If, If/Else, and For Each tasks to handle complex real-world scenarios.
      - task limitations; Keep individual jobs under 1,000 tasks to maintain manageability and performance, using modular design to handle larger workflows.
    - [monitoring & governance practices](./three-pillar-best-practises.png);
      - service principal usage; Use service principals rather than personal accounts for job ownership and data access to ensure continuity and proper access control.
      - comprehensive alerting; Configure alerts for failures, delays, and completions with appropriate escalation and notification strategies.
      - recovery optimization; Leverage Repair & Run capabilities to minimize costs and recovery time when handling failures.
      - parameterization; Design tasks with proper parameterization for maximum reusability and flexibility across environments and use cases.
